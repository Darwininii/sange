Lo que estás describiendo es uno de los problemas más estudiados en bases de datos y sistemas distribuidos. No es realmente un problema de "quién fue primero", sino de **consistencia de datos cuando existen operaciones concurrentes**.

En arquitectura de software este tema pertenece principalmente a:

* Control de concurrencia (Concurrency Control)
* Transacciones (Transactions)
* Aislamiento de transacciones (Transaction Isolation)
* Consistencia de datos (Data Consistency)
* Bloqueos (Locking)
* Control de concurrencia optimista y pesimista (Optimistic/Pessimistic Concurrency Control)
* Condiciones de carrera (Race Conditions)

---

# El problema real

Supongamos que tienes:

```
Producto A
Stock = 10
```

Dos órdenes llegan prácticamente al mismo tiempo.

```
Orden 1
Solicita 10

Orden 2
Solicita 10
```

Ambas ejecutan algo parecido a esto:

```
leer stock

si stock >= cantidad
    descontar
guardar
```

Lo que ocurre es:

```
Tiempo

Orden1 ---- lee 10 -------------------------- guarda 0

Orden2 ---- lee 10 -------------------------- guarda 0
```

Las dos leyeron el mismo valor.

Las dos creen que hay stock.

Las dos descuentan.

Resultado:

Se vendieron 20 unidades.

Cuando solo existían 10.

Esto se llama una **Race Condition**.

---

# ¿Quién fue primero?

En realidad...

**No importa.**

Esa es una idea importante.

En sistemas concurrentes normalmente no intentas descubrir quién fue primero.

Lo que haces es **forzar que exista un primero**.

Es decir, el sistema decide un orden.

Aunque para el usuario ambas compras ocurrieran "al mismo tiempo".

Internamente siempre se serializan.

---

# ¿Cómo lo hacen los bancos?

Imagina una cuenta bancaria.

Saldo:

```
100 €
```

Dos personas intentan retirar

```
100 €

100 €
```

Si ambos leen:

```
saldo = 100
```

Los dos pensarán que pueden retirar.

Eso sería un desastre.

Los bancos utilizan transacciones.

Mientras una operación modifica ese registro...

La otra espera.

# Existen varios métodos

## 1. Pesimistic Locking (Bloqueo Pesimista)

El primero que llega bloquea el registro.

```
Orden1

LOCK Producto

Stock = 10

Descuenta

Stock = 0

UNLOCK
```

Mientras tanto

```
Orden2

Espera...
Espera...
Espera...
```

Cuando finalmente puede leer

```
Stock = 0
```

Entonces responde

```
No hay stock suficiente.
```

Es el método más utilizado para inventarios.

---

## 2. Optimistic Locking

Aquí no se bloquea nada.

Se añade un campo

```
version
```

Ejemplo

```
Producto

id = 5

stock = 10

version = 8
```

Dos órdenes leen

```
version = 8
```

La primera actualiza

```
stock = 0

version = 9
```

La segunda intenta guardar

```
WHERE version = 8
```

Pero ya existe

```
version = 9
```

Entonces la actualización falla.

Debe volver a leer.

Muy usado cuando hay pocas colisiones.

---

## 3. Atomic Update

Este es probablemente el método más elegante para inventarios.

En lugar de hacer

```
leer

validar

guardar
```

Se hace todo en una sola instrucción SQL.

Por ejemplo

```sql
UPDATE productos
SET stock = stock - 10
WHERE
    id = 15
    AND stock >= 10;
```

Después preguntas

```
¿Se actualizó una fila?
```

Si

```
Sí
```

Había stock.

Si

```
0 filas
```

No había stock.

No existe posibilidad de que dos usuarios descuenten el mismo stock.

Porque la base de datos realiza la operación de forma atómica.

Este patrón es muy utilizado.

---

# 4. Serializable Transactions

Es el nivel de aislamiento más alto.

La base de datos actúa como si todas las operaciones ocurrieran una tras otra.

```
Orden1

termina

Orden2

termina

Orden3
```

Nunca simultáneamente.

Muy seguro.

Más lento.

---

# 5. Queue (Cola)

Muchos sistemas grandes hacen esto.

No descuentan directamente.

Todas las compras entran en una cola.

```
Compra A

Compra B

Compra C

Compra D
```

Un único proceso procesa una por una.

```
A

B

C

D
```

Nunca existe competencia.

Amazon utiliza mucho este patrón para algunos procesos.

---

# ¿Cuál usan Amazon, Mercado Libre, etc.?

Generalmente combinan varias técnicas.

Por ejemplo:

```
API

↓

Commit

↓

```

Y además:

* colas

# En tu caso

Supongamos

```
Stock

Tornillo

Cantidad = 5
```

Orden A

```
5 tornillos
```

Orden B

```
5 tornillos
```

No deberías hacer esto:

```
1.
Leer stock

2.
Verificar

3.
Actualizar
```

Porque ambas órdenes pueden leer

```
5
```

En cambio deberías hacer una única operación atómica.

Por ejemplo:

```sql
UPDATE inventory
SET stock = stock - 5
WHERE
    id = 10
    AND stock >= 5;
```

Después:

```
Filas afectadas = 1
```

Entonces la orden continúa.

Si

```
Filas afectadas = 0
```

Entonces:

```
No existe stock suficiente.
```

La segunda orden fallará automáticamente.

No importa cuál llegó primero.

La base de datos decidió cuál obtuvo el bloqueo primero.

---

# Si además manejas órdenes de servicio

Un diseño muy común sería:

```
Inicio transacción

↓

Verificar stock

↓

Descontar stock (UPDATE atómico)

↓

Guardar movimientos de inventario

↓

Guardar productos usados

↓

Cerrar orden

↓

Commit
```

Si cualquiera de esos pasos falla:

```
Rollback
```

Y el stock vuelve exactamente al estado anterior.

---

## Mi recomendación para tu aplicación

Por lo que has contado en conversaciones anteriores (React + Vite en el frontend y un sistema propio de órdenes de servicio e inventario), el enfoque más sólido es:

1. **Nunca descontar el stock desde el frontend.** El cliente solo envía la solicitud.
2. **Realizar toda la lógica en el backend** dentro de una **transacción**.
3. **Usar una actualización atómica** (`UPDATE ... SET stock = stock - ? WHERE stock >= ?`) o un **bloqueo pesimista** (`SELECT ... FOR UPDATE`), según el motor de base de datos.
4. **Confirmar la orden solo si el descuento de stock fue exitoso**; de lo contrario, hacer *rollback* y devolver un error indicando que ya no hay existencias suficientes.

Este patrón es el que utilizan la mayoría de sistemas de inventario porque evita las condiciones de carrera sin necesidad de intentar averiguar "quién fue primero". El propio motor de la base de datos se encarga de establecer un orden seguro de ejecución.
